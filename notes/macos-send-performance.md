# macOS 전송 준비 지연 측정 (2026-10-27)

실제 열린 1:1 카카오톡 창에서 최소화 → 제품의 restoreSendWindow → native read → 입력 포커스까지 측정했다. 본문 설정, Return 이벤트, sendAndMinimize 호출은 없다. Swift는 제품과 같이 -O로 컴파일했고, 메인 Cocoa 이벤트 루프와 AX 작업 스레드를 분리했다. 창의 원래 최소화 상태와 앞에 있던 앱을 시험 종료 때 복구한다. 채팅 내용과 대상 이름은 결과에 기록하지 않는다.

## 관측값

| 방식 | 회차 | 복원 ms | 대화 읽기 ms | 입력 포커스 ms | 준비 합계 ms |
| --- | --- | ---: | ---: | ---: | ---: |
| 기존 최근 60개 행 | 1 | 841 | 4912 | 22 | 5775 |
| 기존 최근 60개 행 | 2 | 824 | 3483 | 18 | 4325 |
| 임시 최근 8개 행 | 1 | 931 | 703 | 5 | 1640 |
| 임시 최근 8개 행 | 2 | 859 | 131 | 0 | 990 |
| 기존 재측정 | 1 | 920 | 4572 | 0 | 5492 |
| 기존 재측정 | 2 | 832 | 3403 | 9 | 4244 |

범위 축소 후 기존 방식을 재측정해도 원래 비용이 재현됐다. 표본은 한 대화방의 작은 비교 실험이며 전송 키, 발신 메시지 확인, 전송 후 최소화, Electron 작업 대기열 시간은 포함하지 않는다. 수치는 전체 실전 전송 속도 개선 보장이 아니다.

## 개선 후보와 우선순위

1. **전송 전·후 전용 읽기**: 현재 sendAndMinimize가 respond를 재사용해 최대 60개 행의 프로필, 발신/수신, 시간, 이름, 본문을 읽고 최근 20개 대화를 만든다. 발송 확인 루프에서도 이 작업을 반복한다. 전송용 경로는 동일 제목의 고유한 창, 지원 채팅 종류, 입력란, 기준 행 식별자, 새 발신 본문과 입력란 비움에 집중할 수 있다. 새 메시지를 찾지 못하면 범위를 넓히며, 불확실한 결과는 계속 unknown으로 남겨야 한다. 일반 수신·그룹 참여자 추적은 기존 문맥 범위를 유지한다. 단순히 모든 읽기를 8개로 제한하는 것은 개선안이 아니다.
2. **전송 우선순위**: MacReader의 현재 FIFO 대기열은 read/list/send를 순서대로 실행한다. 이미 진행 중인 무거운 읽기 뒤에서 전송이 기다릴 수 있다. 전송이 대기하면 새 감지 읽기를 미루고 대기 중 전송을 우선 처리할 수 있다. 진행 중 native 작업을 강제로 중단하거나 동시에 접근하지 않는다. 이 효과는 코드에서 찾은 후보이며 실제 대기 시간을 이번에 측정한 것은 아니다.
3. **확인 반복의 중복 탐색**: 반복마다 창·컨트롤·과거 행 전체를 다시 탐색하기보다 유효성이 확인되는 대상 창/입력란/대화 목록을 재사용하고 필요한 값만 새로 읽는다. 창 제목·현재 포커스·새 발신 본문 대조 및 재시도 금지는 유지해야 한다.

복원 0.82–0.93초(안정화 대기 포함)와 입력 포커스 0–22ms보다 대화 읽기 3.4–4.9초가 우선적인 병목이다. 0.15초 안정화 대기만 줄이는 것은 효과가 작고 앞서 수정한 최소화 전송 문제를 재발시킬 수 있다.

## 재현

- 기존: `node scripts/test-macos-send-preparation.mjs "열려 있는 대상 방 제목"`
- 임시 비교: `node scripts/test-macos-send-preparation.mjs "열려 있는 대상 방 제목" --recent-rows=8`

범위 비교는 임시 디렉터리의 Swift 복사본만 바꾸고 종료 시 삭제한다. 이번 작업은 계측 스크립트와 이 기록을 추가/수정했으며, 제품 전송 로직과 설치 앱은 변경하지 않았다.

## 0.4.10 반영 및 검증

제품에 전송용 SendContext/SendBaseline/newOutgoingMatches와 수동 전송 우선 스케줄링을 구현했다. 준비 단계에서 과거 본문을 해석하지 않고 모든 기존 테이블 자식의 AX 참조를 해시 버킷에 보관한다. 일반 수신 ID 캐시가 비워져도 과거 동일 본문이 새 메시지로 바뀌지 않는다. 전송 후에는 새 행만 확인하며 범위를 8개로 고정하지 않는다. 대화 목록 기준을 얻지 못하면 전송을 중단한다.

캐시를 새로 시작한 제품 함수 경로의 두 번 측정:

| 회차 | 복원 ms | 전송 준비 읽기 ms | 입력 포커스 ms | 준비 합계 ms |
| --- | ---: | ---: | ---: | ---: |
| 1 | 996 | 454 | 19 | 1469 |
| 2 | 842 | 642 | 16 | 1501 |

이전의 기존 경로 4244–5775ms와 비교해 준비 단계는 약 1.5초로 줄었다. 발송 전체 시간 측정은 아니다. 기본 캡처의 캐시를 재사용한 0ms 결과는 비교에 사용하지 않았다.

기존 실제 메시지를 읽기만 해 다음을 검사했다: 전체 기존 행 기준에서는 과거 동일 본문이 일치하지 않음, 해당 발신 행만 기준에서 제외하면 일치함, 다른 본문은 일치하지 않음, 수신 행을 제외해도 발신으로 일치하지 않음. 이 검사는 과거 메시지를 전송하거나 입력하지 않는다. 자동 테스트에서는 활성 읽기를 중단하지 않고 전송을 대기 중 읽기보다 우선 처리하는 순서, 전송 간 FIFO, 응답 오류 후 회복, 타임아웃 이후 아직 동작하는 native 요청과의 동시 실행/자동 재시도 방지 및 읽기 ID의 epoch 유지가 통과했다.
